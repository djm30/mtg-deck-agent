Commander Deck Agent: A Learning Path

Learn agent building by making something you care about. Each stage teaches one concept and ends with something you can demo. You write all the code; the docs and your AI tutor (see AGENTS.md) explain ideas and nudge you along.

Before you start: the one design rule

LLMs propose, code verifies. Commander has hard rules: exactly 100 cards, singleton, color identity, legality. Don't let a model "check" those, because it will get them wrong sometimes. Write plain functions for anything with a correct answer. Use the LLM for judgment calls: synergy, power level, what to cut. Most of what makes an agent reliable comes from this split.
Target shape (you'll grow into this, not build it all at once): user: "Build me a Meren of Clan Nel Toth deck, mid power" │ ▼ [pick/confirm commander] ──(human approves)──▶ [plan: slot budget per role] │ ┌───────────────────────────────────┼─────────────────────┐ ▼ ▼ ▼ Ramp advocate Interaction advocate Synergy advocate └──────────────── proposals + arguments ──────────────────┘ ▼ Judge / curator ▼ validate() in plain code ──fail──┐ │ pass │ ▼ └──▶ back to debate decklist.txt All of it traced in LangSmith (or Langfuse).

Budget

  • 2 hours: Stages 0–3. A working, validated deck builder. This is the core.
  • 4 hours: + Stages 4–5. Agents that debate, and a human who signs off.
  • 6 hours: + Stages 6–8. Deep Agents, evals, and a runnable server.

Each stage has a time box. If you go over it by 50%, take the smallest version that works and move on.

0 · Setup and your first trace

~20 min
Concept

An LLM call is a function: messages go in, a message comes out. Tracing records every call (inputs, outputs, tokens, latency) so you can see what your agent actually did, not what you assume it did. Turn it on now. You'll use it at every stage after this.

Do
  • Python project (uv or venv), a model API key, and a free LangSmith account (Developer plan: 1 seat, 5k traces/month).
  • Set the LangSmith env vars from the quickstart. Make one chat-model call.
Done when

You can open LangSmith and see your call, including the exact prompt and the token count.

Read
  • LangChain overview
  • LangSmith tracing quickstart
  • Free alternative: Langfuse (open source, can self-host).
Reflect
  • What's the difference between a run and a trace in the UI?
  • Where would you look first if a response were slow?

1 · Tools: give the model real card data

~40 min
Concept

A model's knowledge of cards is stale and sometimes made up. A tool is a function plus a description the model reads to decide when and how to call it. An agent is a loop: the model picks a tool, your code runs it, the result goes back to the model, and this repeats until the model answers. This is the ReAct pattern. The tool's name, docstring, and argument types work as a prompt, so write them for the model to read.

Do
  • Write a search_cards tool on top of the Scryfall API. Its query syntax already supports color identity, type, and mana value.
  • Wrap it in an agent using create_agent.
  • Read Scryfall's rules: send a User-Agent header, stay under the rate limit, and return only the fields the model needs.
Done when

"Find 5 green ramp creatures with mana value 3 or less" returns real cards, and the trace shows the tool call(s).

Read
  • Agents · Tools
  • Scryfall API (see "search" and the query syntax page)
Reflect
  • What happens to cost and context when your tool returns the full Scryfall JSON?
  • Change the tool docstring to something vague. How does the agent's behavior change in the trace?

2 · Structured output and a validator

~30 min
Concept

Structured output makes the model return data that matches a schema (for example Pydantic), not free text, so code can use the result. Pair it with a deterministic validator: a plain function that checks the hard rules. The validator's error messages also become feedback for the model in Stage 3.

Do
  • Design a deck schema: commander, and cards each tagged with a role (land, ramp, draw, removal, wipe, synergy, win-con).
  • Write validate(deck) with no LLM in it. It should check 100 cards, singleton (basic lands excepted), color identity, and Commander legality. Return specific, actionable errors.
Done when

You can hand-feed it a broken deck and get back a precise list of what's wrong.

Read
  • Structured output
Reflect
  • Which error message would help a model fix the deck: "invalid deck" or "Sol Ring appears twice; 101 cards, remove 1"? Why?

3 · LangGraph: an explicit workflow with a fix-it loop

~45 min
Concept

The create_agent loop leaves the plan up to the model. LangGraph lets you write the control flow yourself. State is a typed object that every step reads and updates. Nodes are functions. Edges connect them, and conditional edges branch, which is how you get loops. Use a graph when you know the steps. Use an open agent loop when you don't.

Do
  • Build: choose commander → plan slot budget (e.g. ~37 lands, ~10 ramp, ~10 draw, ~10 removal) → fill slots → validate.
  • If validation fails, route back to a "repair" node that receives the errors. Cap the number of retries.
Done when

One command produces a valid 100-card deck, and you can point to at least one repair loop in a trace.

Read
  • LangGraph overview · Graph API (state, reducers, conditional edges)
Reflect
  • What is a reducer, and why does a list of cards in state need one?
  • What stops your graph from looping forever?
2-hour stop. You have a real agent. Stopping here is fine.

4 · Multi-agent debate

~60 min
Concept

Multi-agent means several model "roles", each with its own prompt, tools, and context, coordinated by a pattern: supervisor (one agent delegates), handoffs (agents pass control), or debate (advocates argue and a judge decides). It costs more and is harder to debug. It pays off when the roles really do have conflicting priorities, and deck building has them: ramp vs. interaction vs. synergy, all competing for limited slots.

Do
  • 2–3 advocates, each arguing for its category, plus a judge that resolves the contested slots.
  • Bound it: a fixed number of rounds, and short structured arguments (card, slot, reason, what to cut).
  • Debate only the contested slots, roughly the last 10–15 cards, not all 100.
Done when

You can read a debate transcript in the trace and explain why the judge picked what it picked.

Read
  • Multi-agent patterns
Reflect
  • Did the debate produce a better deck than Stage 3, or just a longer trace? How would you tell?
  • What does each advocate actually need in its context, and what should it not see?

5 · Memory and human-in-the-loop

~30 min
Concept

A checkpointer saves graph state after each step, keyed by a thread. That gives you memory, resumability, and "time travel". An interrupt pauses the graph to wait for a human, and you resume it later with their answer. The human-approval step is what makes an agent safe to use for real decisions.

Do
  • Add a checkpointer. Interrupt after commander selection and again before the final list, so you can approve, swap, or veto cards.
Done when

You can stop the run, come back, say "cut Cyclonic Rift, I hate it," and get a valid deck that respects that.

Read
  • Persistence · Interrupts
4-hour stop. Debate plus human control is the project you set out to build.

6 · Deep Agents: the harness approach

~45 min
Concept

A framework (LangGraph) gives you parts to assemble. A harness (Deep Agents) gives you a ready-made agent with planning (a todo list), a virtual filesystem for scratch notes, and subagents that run in isolated context. Isolated context is the main idea: a subagent can read 200 card results and send back only a summary, so the main agent's context stays small.

Do
  • Rebuild the orchestration with create_deep_agent. Make your advocates subagents and reuse your Stage 1 tool and Stage 2 validator.
  • Have it write the decklist and its reasoning to files.
Done when

You can write a short comparison: what got easier, what you lost control of, and which approach you'd ship.

Read
  • Deep Agents overview · Subagents

7 · Evals: is it actually good?

~30 min
Concept

An eval is a test for non-deterministic output: a dataset of inputs plus evaluators that score each output. Use code evaluators for objective checks (is it valid? does it have at least 10 ramp?). Use LLM-as-judge for subjective ones (does it fit the commander's plan?). Without evals, every prompt change is a guess.

Do
  • A dataset of 5–10 commanders across colors and archetypes.
  • At least one code evaluator and one LLM-judge evaluator. Run it, change a prompt, run it again, and compare.
Done when

You have two experiment runs side by side in LangSmith and can say which version is better.

Read
  • Evaluation quickstart

8 · Make it deployable

~30–45 min
Concept

To deploy an agent you have to serve a stateful, long-running, streaming process, not just put a function behind an endpoint. The LangGraph server handles threads, streaming, interrupts, and background runs. LangGraph Studio is a visual debugger that runs on top of it.

Do
  • Add a langgraph.json and run the local dev server. Drive a run from Studio, including an interrupt.
  • Optional: build a Docker image. Managed hosting on LangSmith needs the paid Plus plan. Self-hosting the container is the free route.
Done when

Someone else could start your agent with one command and talk to it over HTTP.

Read
  • Run a local server
6-hour finish. You've covered the core concepts used in production agents.

Concept glossary

  • Tool: a function plus a schema the model can choose to call.
  • Agent loop / ReAct: the model reasons, calls a tool, sees the result, and repeats until done.
  • Context engineering: choosing what goes into each model call. Most agent quality comes from this.
  • State / node / edge: LangGraph's building blocks: shared data, steps, and routing.
  • Checkpointer / thread: saved state per conversation. Makes memory and resuming possible.
  • Interrupt: pause for human input, then resume.
  • Subagent: a delegated agent with its own isolated context.
  • Harness vs framework: an opinionated, ready-to-run agent vs. building blocks you assemble.
  • Trace / eval: what happened, and whether it was good.
